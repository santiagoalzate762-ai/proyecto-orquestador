# 05.1 Arquitectura y Reglas de Datos — Proyecto Orquestador

## 1. Propósito
Establecer las decisiones de diseño, normas de almacenamiento, activación por etapas y políticas de privacidad que rigen la base de datos del MVP en **PostgreSQL (alojado en Neon)** gestionado con **Prisma ORM 6**.

---

## 2. Decisiones Clave de Diseño

1. **Modelo Relacional Estricto (PostgreSQL en Neon):** Se elige una base relacional porque la información central del producto depende de historiales ordenados, relaciones estrictas entre proyecto, versiones y auditorías, y restricciones de unicidad a nivel de motor (incluyendo índices únicos parciales).
2. **Conexión Dual en Neon (`DATABASE_URL` + `DIRECT_URL`):** Prisma utiliza el endpoint agrupado (*pooled*) para consultas en ejecución y el endpoint directo (`directUrl`) para ejecutar migraciones SQL de forma segura. El comando `prisma db push` queda **prohibido**; todo cambio se aplica mediante `prisma migrate`.
3. **Separación de Tablas por Etapa del MVP:**
   * **Etapa 1A (Base Organizadora — 4 tablas):** `User`, `Project`, `ParentPromptVersion`, `Contract`.
   * **Etapa 1B (Motor Inteligente — 4 tablas):** `UserApiKey`, `UserAiRoleConfig`, `AuditRun`, `AuditFinding`.
4. **Inmutabilidad de Contenido vs. Metadatos de Sincronización:** Las versiones publicadas del **Prompt Padre** (`ACTIVE`/`ARCHIVED`) y los **Contratos Aprobados** (`APPROVED`/`DEPRECATED`) nunca modifican sus campos de contenido (`content`, `schemaJson`, `tsContent`, `httpMethod`, `endpointPath`). Únicamente sus campos de ciclo de vida y sincronización externa (`status`, `syncStatus`, `githubFileSha`, `syncedToGithubAt`, `lastSyncError`, `approvedAt`) pueden actualizarse para reflejar el estado real frente a GitHub.
5. **Doble Representación Consistente de Contratos (`schemaJson` + `tsContent`):** `schemaJson` es la única fuente editable (vía formulario en 1A o IA en 1B); `tsContent` se genera siempre de manera determinista desde `schemaJson` y se muestra al usuario únicamente en modo solo lectura, garantizando que ambas representaciones nunca diverjan.
6. **Identidad Inmutable de Repositorios y Auditorías:**
   * Los proyectos se vinculan mediante `githubRepoId` (no solo por nombre), normalizando `repoOwner` y `repoName` a minúsculas para resistir cambios de mayúsculas o renombramientos.
   * Cada `AuditRun` guarda el `headCommitSha`, `baseCommitSha`, tipo de referencia (`BRANCH`/`PR`), versiones de contratos usadas, modelos usados y rutas analizadas para que todo reporte sea 100% reproducible.
7. **Política de Cero Almacenamiento de Código Fuente:** Ninguna tabla almacena archivos ni extractos literales de código del usuario. Durante una auditoría el *diff* se procesa en memoria y se descarta; en `AuditFinding` solo se persisten rutas, referencias de línea, gravedad y explicaciones en lenguaje humano.

---

## 3. Convenciones de Nomenclatura y Normalización
* **Nombres de tablas (Modelos Prisma):** Singular en `PascalCase` (ej. `AuditRun`, `UserApiKey`).
* **Nombres de columnas:** `camelCase` en Prisma (ej. `projectId`, `createdAt`).
* **Identificadores primarios (PK):** Formato `cuid`.
* **Fechas y horas:** Siempre en **UTC** (`DateTime`).
* **Rutas de carpetas y archivos:** Siempre normalizadas **sin barra inicial ni final** (ej. `"contracts"`, `"frontend"`, `"backend"`, `"contracts/auth-login.contract.ts"`), igualando exactamente el formato que devuelve la API de GitHub.
* **Catálogos cerrados (`Enum`):** 10 tipos `Enum` en PostgreSQL impiden valores fuera de especificación.
