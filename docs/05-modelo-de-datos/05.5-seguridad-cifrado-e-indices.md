# 05.5 Especificación de Seguridad, Cifrado e Índices (PostgreSQL / Neon)

## 1. Cifrado de Secretos (`AES-256-GCM` con `AAD`, `base64` y `keyVersion`)
La plataforma cifra dos secretos sensibles en Neon: el token OAuth de GitHub (`User.githubTokenEncrypted`) y las claves de API de IA (`UserApiKey.encryptedKey`).

* **Llaves Maestras Versionadas (`ENCRYPTION_MASTER_KEY_V1`, `_V2`...):** Cada llave secreta es una cadena de 32 bytes (64 caracteres hexadecimales) almacenada **exclusivamente** en variables de entorno del Backend (`.env` local / secretos de Render). Nunca se guarda en Neon ni en GitHub.
* **Formato Único:** `encryptedKey`/`githubTokenEncrypted`, `iv` (12 bytes aleatorios por registro) y `authTag` (16 bytes) se codifican siempre en **`base64`**.
* **Autenticación de Contexto (`AAD` — *Additional Authenticated Data*):**
  * Para `User`: `AAD = userId`.
  * Para `UserApiKey`: `AAD = "${userId}:${provider}"`.
  * *Propósito:* Impide que un atacante con acceso de escritura a la base de datos copie un texto cifrado de un usuario a la fila de otro usuario para intentar descifrarlo.
* **Procedimiento de Rotación de Llave Maestra:**
  1. Configurar `ENCRYPTION_MASTER_KEY_V2` y `CURRENT_ENCRYPTION_KEY_VERSION=2` manteniendo `ENCRYPTION_MASTER_KEY_V1` disponible para lectura.
  2. Ejecutar el script controlado de migración de secretos que lee registros con `keyVersion = 1`, los descifra con `V1`, los vuelve a cifrar con `V2` (nuevo `iv` + `authTag`) y actualiza `keyVersion = 2`.
  3. Una vez verificados 0 registros con `keyVersion = 1`, retirar `V1`.
* **Advertencia de Respaldo Obligatorio:** La pérdida definitiva de la llave maestra sin respaldo seguro (gestor de contraseñas / bóveda de secretos) hace irrecuperables los tokens y claves cifrados; los usuarios tendrían que volver a iniciar sesión en GitHub y reingresar sus claves de IA.
* **Regla de Cero Exposición:** Ningún controlador ni log puede emitir `githubTokenEncrypted`, `encryptedKey`, `iv`, `authTag`, `orq_session` ni llaves maestras.

## 2. Índices de Rendimiento y Unicidad en PostgreSQL (Neon)

| Tabla | Columnas indexadas | Tipo | Para qué sirve |
| :--- | :--- | :--- | :--- |
| `User` | `(githubId)` | Único | Login instantáneo por GitHub OAuth. |
| `Project` | `(userId, githubRepoId)` | Único compuesto | Impide conectar dos veces el mismo repo y cubre consultas del Dashboard por `userId` (sin índice redundante aparte). |
| `ParentPromptVersion` | `(projectId, versionNumber)` | Único compuesto | Evita duplicar versiones (`v1`, `v2`). |
| `ParentPromptVersion` | `(projectId) WHERE status = 'ACTIVE'` | **Único parcial (SQL)** | Garantiza a nivel de PostgreSQL **máximo 1 Prompt Padre `ACTIVE` por proyecto**. |
| `ParentPromptVersion` | `(projectId, status)` | Normal compuesto | Consulta rápida de la versión vigente. |
| `Contract` | `(projectId, moduleName, versionNumber)` | Único compuesto | Evita duplicar versiones de un mismo módulo. |
| `Contract` | `(projectId, moduleName) WHERE status = 'APPROVED'` | **Único parcial (SQL)** | Garantiza a nivel de PostgreSQL **máximo 1 Contrato `APPROVED` por proyecto y módulo**. |
| `Contract` | `(projectId, status)` | Normal compuesto | Filtra contratos aprobados para auditorías y regeneración de `agents.md`. |
| `UserApiKey` | `(userId, provider)` | Único compuesto | Una clave activa por proveedor y usuario. |
| `AuditRun` | `(projectId, createdAt DESC)` | Normal compuesto | Carga rápida del historial ordenado del más reciente al más antiguo. |
| `AuditFinding` | `(auditRunId, severity)` | Normal compuesto | Muestra primero hallazgos `CRITICAL` y `HIGH`. |

### SQL obligatorio en la migración inicial de Prisma
Como Prisma no expresa índices únicos parciales en su sintaxis declarativa, **ambos deben incluirse en la migración SQL** (razón por la cual `prisma db push` está prohibido):

```sql
CREATE UNIQUE INDEX unique_active_prompt_per_project
ON "ParentPromptVersion" ("projectId")
WHERE status = 'ACTIVE';

CREATE UNIQUE INDEX unique_approved_contract_per_module
ON "Contract" ("projectId", "moduleName")
WHERE status = 'APPROVED';
```

## 3. Transacciones Atómicas y Orden Obligatorio (`prisma.$transaction`)

Para no chocar con los índices únicos parciales ni sufrir condiciones de carrera:

1. **Crear proyecto + Prompt Padre `v1`:** Insertar `Project` + insertar `ParentPromptVersion` (`versionNumber = 1`, `status = ACTIVE`, `syncStatus = PENDING`) en la misma transacción.
2. **Publicar nueva versión del Prompt Padre:**
   * **Paso 1:** Cambiar versión `ACTIVE` anterior a `ARCHIVED`.
   * **Paso 2:** Cambiar el nuevo `DRAFT` a `ACTIVE` (`syncStatus = PENDING`) y marcar `Project.agentsMdSyncStatus = PENDING`.
3. **Aprobar nueva versión de Contrato:**
   * **Paso 1:** Cambiar versión `APPROVED` anterior del mismo `(projectId, moduleName)` a `DEPRECATED`.
   * **Paso 2:** Cambiar el nuevo `DRAFT` a `APPROVED` con `approvedAt = now()`, `syncStatus = PENDING` y marcar `Project.agentsMdSyncStatus = PENDING`.
4. **Eliminar una clave de IA (`UserApiKey`):** Borrar la clave + poner en `null` las columnas de `UserAiRoleConfig` que apunten a ese mismo `provider`.
5. **Guardar resultado de Auditoría:** Crear `AuditRun` + insertar todos sus `AuditFinding` en la misma transacción.
6. **Manejo de colisión de numeración (`versionNumber`):** Si dos pestañas intentan crear simultáneamente la misma versión (`MAX + 1`), PostgreSQL lanzará violación de unicidad (`P2002`). El Backend captura el error y responde **`409 VERSION_CONFLICT`** para que el cliente recargue o reintente limpiamente.
